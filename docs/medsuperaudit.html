01 Executive Summary

The backend is substantially further along than either repository's documentation claims, and the patient-facing half of the Flutter client is genuinely wired to it. The booking spine — search, doctor detail, slots, hold, confirm, cancel, reschedule, list — is real on both sides with matching contracts and server-enforced ownership. That is the strongest part of the system and it is close to done.

It is nonetheless not production-ready, for six independently disqualifying reasons, each verified in code today:

identity-auth.module.ts:75 binds OTP_SENDER to LoggingOtpSender, which writes the code to the server log and sends nothing. No SMS provider is chosen (File 10 Part 4, open decision).

Every journey in the product begins at login. Nothing downstream is reachable by a real user.

03 Verified Current Architecture

Backend — a modular monolith, exactly as CLAUDE.md describes, and the description holds up against the code. One API process (src/main.ts, global prefix /v1) and one worker (src/worker.ts). Cross-cutting concerns are registered once in CoreModule in a real, verified order: ThrottlerGuard → JwtAuthGuard → RbacGuard → ValidationPipe → handler → ResponseInterceptor / ErrorEnvelopeFilter. Seven domain modules are registered in app.module.ts; notifications/ and delivery/ contain a README and nothing else.

Frontend — clean architecture with Riverpod 3, one entry point, one binary. The two-flavor split described in older docs is genuinely gone. Every request passes through a fixed Dio chain: CorrelationId → Auth → Idempotency → [Mock] → ResponseEnvelope → Logging → Error → Retry. The envelope interceptor correctly unwraps the backend's {success, data, requestId, correlationId} shape.

Quality of what exists

Where the backend is built, it is built well and the engineering claims hold. Verified by reading the chain end to end:

  • Authorization is genuinely server-side. RbacGuard enforces @Roles()/@Permissions() against token claims; a route with neither is authenticated-only, fail-closed by default.
  • Ownership scoping is real. GetAppointmentUseCase checks appointment.patient_id !== actor.sub; pharmacy orders and prescriptions do the same, and all three throw NotFoundError rather than Forbidden, so existence is not leaked.
  • Concurrency primitives are DB-enforced, not app-checked: partial unique index on active holds, version-guarded first-accept-wins on broadcasts, optimistic locking on every stateful table.
  • Error handling is centralized in one filter; no raw Prisma error or stack trace reaches a client.

The gap is not craft. It is that four external dependencies were never chosen, one config flag defaults to off, and one build flag is invalid.

05 Frontend Readiness Report

Analysis passes cleanly — 0 errors across 63 screens — and the l10n catalogs are symmetric at 648 keys with full RTL and an ar start locale. Session state is derived from the server (GET /v1/auth/me), not from what the user tapped on the login screen, which is the right call. Logout carefully invalidates 15 non-autoDispose providers to prevent one account's data leaking into the next session — a real bug that was found and fixed.

UI that reports success the backend never persisted

The audit brief asks for this explicitly. Three concentrations, all reachable in the default dev configuration:

F-1Provider schedule editor and clinic settingsHigh
Evidence
provider_schedule_editor_screen.dart:69 shows «تم تحديث جدول المواعيد بنجاح» after PATCH /v1/provider/schedule; provider_clinic_settings_screen.dart:80 does the same for /v1/provider/clinic-settings. Neither route exists on the backend.
Impact
A doctor believes their availability has been published. Real availability is only editable through POST/PATCH /v1/schedule-templates, which is Admin-only. Against a real backend this 404s instead — so the failure mode flips from silent to loud, but is never correct.
F-2The entire wallet — including a deposit flowHigh
Evidence
14 screens and wallet_remote_datasource.dart calling 7 /v1/wallet/* endpoints with 0 backend references. The mock keeps a running balance in _MockWalletStore, so a deposit visibly increases it.
Mitigation
The feature is currently unreachable — no route in lib/app/router/routes/ registers any wallet screen and nothing navigates to one. It is dead code, not a live deception. That is luck rather than design.
F-3Lab booking confirmationHigh
Evidence
/patient/lab/* routes are registered and reachable. POST /v1/lab-bookings returns a mock confirmation with a booking reference.
Impact
A patient completes a lab booking and receives a reference number for an appointment that does not exist in any system.

Cross-cutting frontend gaps

  • No offline behavior at all. CachePolicy and the outbox/ package (OutboxBox, PendingAction, SyncService) are declared and provider-registered, and consumed by exactly zero features.
  • No push notifications and no crash reporting in practice. FcmService, LocalNotificationService, NotificationPriorityRouter and CrashlyticsService are all Riverpod providers that nothing reads. No FCM token is ever registered, and bootstrap.dart installs no FlutterError.onError hook.
  • Pagination is dropped everywhere. nextCursor is parsed and discarded in appointments; pharmacy order listing reads only the first page by construction.
  • 22 hardcoded Arabic strings in provider_dashboard bypass the l10n catalog.

13 Security and RBAC Findings

The headline is good: roles come from the server. SessionController discards the role the user picked at login and re-reads it from GET /v1/auth/me. The client's route guard is a convenience layer over an authorization boundary that is genuinely enforced in RbacGuard, and every ownership check throws NotFoundError rather than Forbidden, so resource existence is not disclosed. No IDOR was found on any patient-scoped resource.

S-1Idempotency and OTP rate limiting are off by defaultCritical
Detail
See P0-3. Two guards depend on RedisService: IdempotencyInterceptor honours the enabled flag and degrades to a silent pass-through, while PhoneRateLimiterService bypasses the flag and calls redis.client.incr directly — so the two behave inconsistently under the same configuration.
Impact
Duplicate payment captures and appointment confirmations; OTP-request flooding is unbounded whenever Redis is unreachable rather than merely disabled.
Action
Add REDIS_ENABLED to env.validation.ts with a production-mandatory default of true; fail boot rather than degrade. Route the rate limiter through the same guarded accessor.
S-2Approving a doctor silently revokes their patient identityHigh
Detail
RoleMembershipRepository.findActiveByUser orders created_at desc and both VerifyOtpUseCase and RefreshTokenUseCase take memberships[0]. After Admin verification the newer DOCTOR membership always wins.
Impact
A verified doctor can no longer book an appointment, upload a prescription, or order from a pharmacy — every one of those routes is @Roles(PATIENT). Their existing appointments become unreadable. The repository comment concedes this is "the concrete choice made in its absence, not a documented spec."
Action
Product decision (§19-4), then an explicit context-selection endpoint or multi-context tokens.
S-3Release builds can ship the mock transportHigh
Detail
See P0-5. Nothing couples AppConfig.isProduction to AppConfig.isMock.
Impact
A build that accepts OTP 123456 and fabricates every response could reach a store listing. Credentials typed into it are validated by nothing.
Action
Add an assertion in bootstrap.dart that hard-fails when isMock && !kDebugMode; put BASE_URL in the launch configs and the release pipeline.
S-4Prescriptions are readable by any pharmacy staff memberMedium
Detail
GetPrescriptionUseCase grants access on contextType === 'PHARMACY_STAFF' || 'ADMIN' with no branch scoping, and GET /v1/prescriptions returns the global QUALITY_CHECK_PASSED queue.
Impact
Staff at any verified pharmacy can read every patient's prescription images and items, including orders broadcast to competitors. Deliberate for a shared review queue; still a health-data exposure worth an explicit decision.
Action
Scope the queue to branches the order was actually broadcast to, or record an accepted-risk decision.
S-5CORS reflects any origin unless explicitly configuredMedium
Detail
main.ts falls back to origin: true with credentials: true when CORS_ALLOWED_ORIGINS is unset. Production logs a warning and continues. The key is absent from .env.
Impact
Wildcard-equivalent CORS on a credentialed API. The warning is correct and the mitigation is one env var — but a warning is not a control.
Action
Make the allowlist mandatory when NODE_ENV=production.
S-6Access tokens are secure at rest; the session flags are notInformational
Detail
Tokens live in flutter_secure_storage, correctly. Onboarding, password-complete and doctor-registration flags live in a Hive box, and logout deletes them explicitly — a leak between accounts on a shared device was already found and fixed here.
Impact
None currently; the flags are UX state, not authorization. Worth keeping that boundary as more state accumulates.

15 Database Persistence Gaps

  • Accepted but never persisted, by design and echoed back honestly: provider registration returns notPersisted: ['specialty_label','documents','city_label','working_days']. A doctor's submitted working days and uploaded credential documents are discarded — the client shows a completed 4-step wizard regardless.
  • Fabricated rather than absent: prescription_items rows are written from the OCR stub, so the data is present in the database and wrong.
  • Emitted and never consumed: outbox_events accumulates 10 event types indefinitely. This is expected per CLAUDE.md, but the table grows without bound and nothing prunes it.
  • Client-side only: onboarding completion, password completion, and doctor-registration-submitted are Hive flags with no server column. Reinstalling the app resets them; only the last is re-derivable from the backend.
  • Schema without logic: postponed.prisma carries DeliveryOrder, Review, HealthRecord, Encounter, Consent, FraudFlag and the family-accounts models. No wallet table exists in any schema file.
  • Migration hygiene is sound: 14 migrations, forward-only, with the concurrency indexes (active-hold partial unique, slot start_at unique, pharmacy queue indexes) present as real migrations rather than manual DDL.

22 Short Non-Technical Management Summary

MedSuper is further along than its own documentation suggests, and the quality of what exists is good. A patient can be registered, find a doctor, see real availability, book, confirm, cancel and reschedule an appointment, upload a prescription and place a pharmacy order — and all of that is genuinely connected to a real server with real database records and correct security. That is the hard part of a healthcare platform, and it is essentially done.

It cannot launch today, for reasons that are unusually concentrated rather than spread thin.

The single biggest issue: nobody can log in. The system generates a verification code correctly but has no way to send it, because no SMS provider has been selected. Everything else in the product sits behind that door. This is a purchasing decision, not an engineering problem, and the code to use it is already in place — roughly two days of work once a provider is chosen.

The second: pharmacy orders currently contain placeholder medication data. Because no prescription-reading service was selected, a temporary stand-in inserts a fake medication line so orders can be created at all. This must be closed before any real patient uses the pharmacy flow. The safer, cheaper path is to have a pharmacist type the medications in — the screens and rules for that already exist.

The third: three configuration and build defects that together mean the server cannot be packaged for release, duplicate taps can create duplicate bookings and duplicate charges, and doctor search fails outright. All three are small and fixable within a week, with no decisions required.

Separately, about four in ten of the app's screens talk to endpoints that were designed but never built — principally the doctor's dashboard, a wallet, and lab booking. They work convincingly in demos because the app ships with a built-in simulator. The wallet is currently unreachable from the app, which limits the damage; lab booking is not, and a patient can complete a lab appointment that exists nowhere.

Recommended sequence: choose an SMS provider this week, and decide whether pharmacists will enter prescriptions manually. In parallel, fix the three build and configuration defects, which need no approval. That combination turns a working demo into a launchable patient product in roughly three weeks. The doctor-facing half needs about a month more, and depends on decisions about what a doctor should actually be able to do in the app.

One process recommendation. Three separate documents in this codebase state that a feature was verified against the real backend when it was in fact only checked against the documentation or the built-in simulator — and one of those, doctor search, is broken today because of it. The STATUS.md convention is genuinely valuable and worth keeping; it needs a rule that "verified" means a dated run against a deployed server, and nothing else.
